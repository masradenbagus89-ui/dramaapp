### 4. 🚀 Deployment (Vercel / Railway / Render / Cloudflare Pages) (deteksi: `vercel.json`, `render.yaml`, `railway.json`)
- **Env var per-environment** (prod/preview/dev) di dashboard platform, BUKAN di repo; jangan pernah commit `.env`.
- **Build reproducible:** lockfile + versi runtime dikunci & di-commit.
- **Healthcheck + rencana rollback 1-baris;** pakai preview deploy untuk tiap PR sebelum tayang ke prod.
- **Strategi rilis tanpa putus** (default rolling: ganti instance bertahap; blue-green/canary untuk yang berisiko).
- **🚨 Denial-of-Wallet (serangan biaya, khas serverless).** Beda dari serangan biasa yang bikin situs TUMBANG, ini bikin **TAGIHAN MELEDAK**: serverless (Vercel/Railway) auto-scale mengikuti lalu lintas → penyerang membanjiri permintaan / memanggil fungsi mahal (LLM, ekspor, gambar) → biaya membengkak walau situs "baik-baik saja". Mitigasi: **(1) batas anggaran + alert biaya** di platform (mis. Vercel Spend Management / batas usage Railway — cek fitur versi terpasang); (2) **rate-limit per-user + cap concurrency** (batas jumlah proses bersamaan); (3) cache/CDN untuk yang berulang; (4) WAF/bot-filter + `robots`/challenge untuk endpoint mahal; (5) batas ukuran & durasi fungsi. Fitur LLM → batas token/biaya (`workflows/cap/ai-rag-aman.md`). (🙂 taksimu argonya jalan tiap ada penumpang — pasang batas harian + alarm biar tak "disuruh keliling kota" tanpa henti oleh iseng.)
- **Subdomain takeover (pengambilalihan sub-domain terlantar).** Sub-domain (mis. `promo.domainmu.com`) yang lewat DNS masih menunjuk (`CNAME`) ke layanan PaaS yang **sudah kamu hapus** (Vercel/Netlify/S3) bisa **diklaim penyerang** → ia pasang situs phishing ATAS NAMA domainmu. Mitigasi: **hapus DNS record saat mematikan layanan**; audit berkala **CNAME "dangling"** (menunjuk ke tujuan kosong); jangan tinggalkan subdomain preview lama menunjuk layanan mati. (🙂 jangan biarkan papan nama tokomu tetap terpasang di ruko yang sudah kamu tinggalkan — orang lain bisa buka toko palsu di situ pakai namamu.)
- 🙂 Non-Programmer: simpan kunci di "brankas" platform (bukan di kode); tiap kirim ke server punya tombol "balik ke versi lama"; coba dulu di "panggung latihan" (preview) sebelum tayang ke publik.

#### 🔒 Gerbang keamanan otomatis di pipeline (SAST · SCA · secret · container · DAST · SBOM)

> Uji kode CEPAT & OTOMATIS tiap PR — jauh lebih murah daripada ketahuan setelah bocor. Tiap alat menutup lapisan berbeda; tak perlu semua sekaligus (lihat label WAJIB/DISARANKAN/OPSIONAL).

- 👨‍💻 Programmer:
  - **SCA — dependency rentan (WAJIB).** Cek CVE (celah publik) di paket pihak-ketiga. Kit SUDAH: `npm audit` + `govulncheck` (Go) via `npx lintasai stack-check`. TAMBAH untuk berkelanjutan: **Dependabot/Renovate** (PR otomatis saat ada versi patch) + `pip-audit` (Python). = OWASP A03:2025 (§4.14-5).
  - **SAST — baca kode cari celah (DISARANKAN).** SAST (*Static Application Security Testing* = periksa kode TANPA menjalankannya). Kit SUDAH: `bandit` (Python). TAMBAH untuk JS/TS: `semgrep --config auto` (multi-bahasa, cepat) atau **CodeQL** (gratis untuk repo publik / GitHub Advanced Security). Cek nama paket di registry sebelum pasang (§8.2).
  - **Secret scan (WAJIB).** Kit SUDAH: pre-commit `secret-guard` + workflow CI (cegah `.env`/kunci ter-commit). Pelengkap server-side: GitHub Secret Scanning.
  - **Container scan (kalau pakai Docker).** `trivy image <img>` = pindai CVE base image + dependency; jalankan di CI sebelum push image (lengkapi Dockerfile §bawah).
  - **DAST — uji app BERJALAN (OPSIONAL, untuk app publik matang).** DAST (*Dynamic …* = "serang" app hidup di staging). **OWASP ZAP** baseline scan; berat → jadwalkan berkala, bukan tiap PR.
  - **SBOM — daftar-isi dependency (OPSIONAL).** Hasilkan CycloneDX (`@cyclonedx/cyclonedx-npm`) → saat ada celah paket global (mis. Log4Shell), cepat tahu "apakah kita terdampak?". = A03:2025.
- 🙂 Non-Programmer: pasang "alat pemindai otomatis" di ban berjalan kode — ada yang cek "bahan baku busuk" (dependency), yang baca "resep" cari kesalahan (SAST), yang endus "kunci nyasar" (secret), yang periksa "kemasan" (container), dan yang coba "menyerang toko latihan" (DAST). Wajib minimal 2 pertama; sisanya menyusul sesuai kebutuhan.
- *Sumber: praktik DevSecOps / OWASP (bukan ECC) — nama alat diverifikasi ada.*

#### ☁️ Keamanan infra cloud (IAM · WAF · backup/DR)

> Aplikasi aman tapi "gedung"-nya bocor = sama saja bocor. 3 blok: pengaturan akun cloud, pagar depan, cadangan data — disuling untuk stack PaaS terkelola (Vercel/Railway/Render + Cloudflare + Supabase), bukan AWS mentah.

- 👨‍💻 **Akses akun cloud (IAM = *Identity & Access Management*, pengaturan siapa-boleh-apa):**
  - **MFA WAJIB** di semua akun admin: GitHub org, Vercel/Railway/Render, Supabase, Cloudflare, registrar domain. Akun root/owner JANGAN dipakai kerja harian — buat akun per-orang dengan hak minimum (default deny §5).
  - **Token API ber-scope sempit + berumur pendek**; untuk CI→cloud pakai **OIDC** (saling-percaya antar-layanan TANPA menyimpan kunci berumur-panjang — kit sendiri memakainya untuk publish npm). `GITHUB_TOKEN` di workflow: blok `permissions:` minimum — sudah dicontohkan template CI/CD di atas.
  - **Tinjau akses berkala:** staff keluar = cabut aksesnya HARI ITU; token/kredensial tak terpakai = hapus; audit "siapa pegang apa" tiap kuartal.
- 👨‍💻 **Pin action pihak-ketiga ke commit SHA penuh (supply-chain CI).** Tag (`@v45`) BISA DIPINDAH penyerang — insiden nyata `tj-actions/changed-files` (CVE-2025-30066, Mar 2025, CVSS 8.6 + masuk katalog KEV CISA): tag v1–v45.0.7 dialihkan ke commit jahat yang membocorkan secret ke log CI ribuan repo. Dok resmi GitHub: SHA penuh = "satu-satunya cara memakai action sebagai rilis kekal (immutable)". Praktik: `uses: pihak/aksi@<sha-40-digit> # v45.0.7` + biarkan Dependabot yang menaikkan SHA-nya. Action resmi (`actions/*`) berisiko lebih rendah — prioritaskan pin-SHA untuk pihak-ketiga.
- 👨‍💻 **WAF Cloudflare (*Web Application Firewall* = penyaring serangan di depan situs):** aktifkan **managed ruleset** — sadar-plan (dicek 2026-07): plan Free hanya dapat "Free Managed Ruleset" (celah high-impact saja); **Cloudflare Managed Ruleset + OWASP Core Ruleset butuh plan Pro ke atas**. Lengkapi: rate limiting rules + bot protection + mode SSL/TLS **Full (strict)**. WAF = lapisan TAMBAHAN di depan, BUKAN pengganti validasi di server (§8).
- 👨‍💻 **Backup/DR (*Disaster Recovery* = rencana pulih dari bencana):**
  - **Supabase** (dicek 2026-07): backup harian otomatis HANYA plan berbayar — Pro 7 hari · Team 14 · Enterprise 30; **plan Free TIDAK di-backup otomatis** → wajib ekspor manual/terjadwal via CLI. Butuh pulih presisi? **PITR** (*Point-in-Time Recovery* = mundur ke titik waktu tertentu) = add-on Pro+ (butuh compute Small+; arsip WAL tiap 2 menit → data hilang terburuk ~2 menit; catatan: PITR MENGGANTIKAN backup harian).
  - **Uji-restore berkala (minimal tiap kuartal):** backup yang tak pernah diuji-pulihkan = BELUM punya backup. Latih pulihkan ke project staging + tulis langkahnya jadi runbook (`docs/runbooks/`).
  - **Tetapkan 2 angka keputusan-OWNER (bukan teknisi): RPO** (*Recovery Point Objective* = maksimal data yang rela hilang, mis. "1 jam terakhir") + **RTO** (*Recovery Time Objective* = maksimal lama boleh mati, mis. "4 jam") — semua setelan backup mengikuti 2 angka ini.
  - **Proteksi-hapus:** CI/staff junior JANGAN diberi hak menghapus project/DB produksi; aset non-DB (file upload di storage) ikut di-backup — database pulih tapi foto pelanggan hilang = tetap bencana.
- 🙂 Non-Programmer: tiga lapis "keamanan gedung" server — (1) kunci ruangan dibagi per-orang seperlunya, kunci-master disimpan bukan dipakai harian; (2) pagar penyaring tamu di depan situs; (3) salinan cadangan data yang RUTIN dicoba dipulihkan — plus dua angka keputusan bisnis: berapa banyak data rela hilang + berapa lama toko boleh tutup.
- *Sumber: ECC `security-review/cloud-infrastructure-security.md` (MIT © Affaan Mustafa) — disuling untuk stack PaaS tim; contoh AWS IAM/VPC/Terraform dibuang (niche). Fakta layanan (WAF per-plan Cloudflare, backup/PITR Supabase, pin-SHA GitHub, CVE-2025-30066 di NVD) diverifikasi ke dok resmi 2026-07 — fitur per-plan bisa berubah, cek ulang plan terpasang.*

#### 🩺 §health — Validasi env fail-fast + health check berlapis

> Pelengkap `templates/OBSERVABILITY_PRODUKSI.md` Pilar 3 (yang sudah punya `/api/health` sederhana). Yang **ditambah di sini**: (a) tolak env salah SEBELUM app hidup, (b) health check DALAM (cek database) buat monitoring internal.

**1. Validasi env saat startup (fail-fast) — zod v4**

- 👨‍💻 Programmer: validasi SEMUA *environment variable* (setelan rahasia dari luar kode: alamat DB, kunci) sekali di startup pakai schema. Kalau ada yang salah/kosong → app **BERHENTI di titik itu** dengan pesan jelas, bukan `undefined` yang meledak jauh di dalam alur (susah dilacak). *fail-fast* = gagal secepat & sejelas mungkin di pintu masuk.

```ts
// lib/env.ts — dipanggil PALING AWAL (sebelum server mulai menerima request)
import * as z from "zod";
const envSchema = z.object({
  NODE_ENV: z.enum(["development", "test", "staging", "production"]),  // 'test' WAJIB — Jest/Vitest set NODE_ENV=test; sesuaikan daftar ke environment project kamu
  PORT: z.coerce.number().default(3000),   // process.env selalu string → coerce jadi angka
  DATABASE_URL: z.url(),                    // zod v4: z.url()  |  zod v3: z.string().url()
  JWT_SECRET: z.string().min(32),           // rahasia < 32 huruf = DITOLAK saat start
  LOG_LEVEL: z.enum(["debug", "info", "warn", "error"]).default("info"),
});
export const env = envSchema.parse(process.env); // gagal di sini = app berhenti + error jelas
```
- 🙂 Non-Programmer: satpam cek SEMUA "kunci" (kata sandi, alamat database) di pintu masuk; kalau ada yang palsu/hilang, gedung TIDAK dibuka — bukan roboh di tengah acara saat pengunjung sudah ramai (jauh lebih sulit ditelusuri).

> ⚠️ **Sadar-versi:** contoh pakai **zod v4** (`z.url()`). Project masih **zod v3**? ganti `z.url()` → `z.string().url()`. Cek versi terpasang: `npm ls zod`.

**2. Health check berlapis (`/api/health` + `/api/health/detailed`)**

- 👨‍💻 Programmer: `/api/health` = cek CEPAT (buat *load balancer* (pembagi beban lalu lintas ke banyak server) / uptime monitor — balikan 200 selama proses hidup). `/api/health/detailed` = cek DALAM (ping DB/redis; balikan **503** kalau ada yang sakit, plus `version` + `uptime`) buat monitoring internal. (Di Next.js App Router, berkas `app/api/health/route.ts` **pasti** ter-map ke URL `/api/health` — bukan `/health`; samakan alamat di uptime monitor & probe.)

```ts
// app/api/health/route.ts — cek CEPAT
export async function GET() { return Response.json({ status: "ok" }); }
```

> ⚠️ **BERKAS TERPISAH** — snippet `detailed` di bawah tinggal di `app/api/health/detailed/route.ts`, BUKAN berkas yang sama dengan di atas. Jangan tempel keduanya ke satu berkas: dua `export async function GET` dalam satu berkas = error build **"Duplicate export GET"**.

```ts
// app/api/health/detailed/route.ts — cek DALAM
import { db } from "@/lib/db";            // WAJIB: klien DB project (Prisma: '@/lib/db'). Tanpa baris ini → build gagal "Cannot find name 'db'".
async function cekDB() {
  try { await db.$queryRaw`SELECT 1`; return { status: "ok" as const }; }
  catch { return { status: "error" as const, pesan: "DB tak terjangkau" }; }
}
export async function GET() {
  const checks = { database: await cekDB() };
  const sehat = Object.values(checks).every((c) => c.status === "ok");
  return Response.json(
    { status: sehat ? "ok" : "degraded", version: process.env.APP_VERSION ?? "unknown",
      uptime: process.uptime(), checks },
    { status: sehat ? 200 : 503 },  // 503 = "aku belum siap" → orchestrator tak kirim traffic
  );
}
```
- 🙂 Non-Programmer: dua jenis "cek detak jantung" — yang cepat (masih hidup atau tidak) dan yang teliti (organ dalam sehat? mis. koneksi database). Kalau organ dalam sakit, app bilang "jangan kirim pelanggan ke saya dulu" (kode 503).

> 🔒 **Keamanan:** di Next.js/Vercel, route seperti ini **publik secara default**. `/api/health/detailed` membocorkan lebih dari sekadar `version`: `uptime` dan status hidup/mati DB pun sebaiknya TAK terbuka untuk anonim (peta permukaan-serang gratis). **Mitigasi UTAMA — batasi akses:** token/middleware, atau kunci ke jaringan internal monitoring (endpoint hanya terjangkau uptime monitor, bukan publik). Membuang `version` cuma **pelengkap** (menutup satu petunjuk pencocokan celah per-versi), BUKAN pengganti pembatasan akses — sebab `uptime` + status DB tetap bocor. (Selaras §8 kit: jangan bocorkan info sistem.)

**Kubernetes** (kalau pakai): pisahkan 3 *probe* (pemeriksa berkala) — `liveness` (restart kalau macet), `readiness` (boleh terima traffic?), `startup` (beri waktu start lama sebelum dinilai). Arahkan `liveness`/`startup` ke `/api/health` (cepat, jangan yang cek-DB → hindari restart beruntun saat DB dipakai bersama); `readiness` boleh ke `/api/health/detailed` bila ingin 503-saat-DB-sakit benar-benar menarik pod dari traffic (sadar efek beruntun bila DB shared ikut mati).

#### 🐳 Dockerfile produksi (multi-stage) — 5 aturan wajib

- 👨‍💻 Programmer: kalau kemas app pakai Docker, image produksi WAJIB: (1) **multi-stage** (deps → build → runner) biar image kecil; (2) **user non-root** (`adduser` + `USER`); (3) **`HEALTHCHECK`** nembak `/api/health`; (4) **pin base image** (`node:24-alpine`, BUKAN `:latest`; node:20 sudah EOL); (5) **`.dockerignore`** (buang `node_modules`/`.env*`/`.git`). ### Caching & Revalidate Next.js (sadar-versi) — pembeda app "powerful" vs lambat/basi
- Pilih SADAR per-halaman: **static** (default, tercepat, konten jarang berubah) · **ISR** (`export const revalidate=<detik>`, boleh basi sebentar) · **dynamic** (`force-dynamic`, per-user/real-time).
- **Sesudah MUTASI (Server Action/route) → invalidasi terarah:** `revalidateTag('<tag>')` (fetch pakai `{next:{tags:[...]}}`) / `revalidatePath('/path')`. Tanpa ini → user lihat data BASI ("kok belum berubah?").
- ⚠️ **Default caching BERUBAH antar-versi Next** (`fetch` tak lagi di-cache default di 15+; `'use cache'` eksperimental) — WAJIB cek versi TERPASANG, jangan dari ingatan (§8.2).
- Cache = tuas LCP/TTFB (lengkapi Web Vitals); tapi cache respons per-user tanpa scope = data bocor antar-user → JANGAN.
